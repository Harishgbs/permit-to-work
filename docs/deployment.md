# Deployment guide

Architecture:

- Frontend: Vercel, built from `vercel.json` in the repository root.
- API: Render Node web service, defined by `render.yaml`.
- Database: Neon PostgreSQL, configured manually in the Neon and Render dashboards.

Never commit `.env` files or paste secrets into chat. The Blueprint generates `JWT_SECRET` in Render and leaves `DATABASE_URL` and `CORS_ORIGIN` for secure dashboard entry.

## Required environment variables

| Platform | Variable | Purpose |
| --- | --- | --- |
| Neon | none in repository | Create the PostgreSQL database and copy its pooled connection string securely. |
| Render | `DATABASE_URL` | Production Neon connection string. Enter only in the Render dashboard. |
| Render | `JWT_SECRET` | Generated by the Blueprint in Render; keep it private. |
| Render | `CORS_ORIGIN` | Exact Vercel frontend origin, such as `https://<project>.vercel.app`, without a trailing slash. |
| Render | `NODE_ENV` | Set to `production` by the Blueprint. |
| Render | `NODE_VERSION` | Set to `22` by the Blueprint. |
| Render | `PORT` | Provided automatically by Render. |
| Render | `JWT_EXPIRES_IN` | Optional; defaults to `1h`. |
| Render | `EXPIRY_SCAN_INTERVAL_MS` | Optional; defaults to `60000`. |
| Vercel | `VITE_API_BASE_URL` | Full deployed API base URL including `/api`, for example `https://<service>.onrender.com/api`. |

## Neon setup

1. Sign in to Neon and create a new project for this assignment.
2. Create a separate production database; do not use the local Podman database.
3. Copy the pooled PostgreSQL connection string from the Neon dashboard.
4. Keep that value private and enter it only into Render when prompted.

## Render API setup

1. In Render, choose **New +** then **Blueprint**.
2. Connect the GitHub repository `Harishgbs/permit-to-work`.
3. Select the `main` branch and continue.
4. Render reads `render.yaml` and prompts for `DATABASE_URL` and `CORS_ORIGIN`.
5. Paste the Neon connection string into `DATABASE_URL`.
6. Enter the final Vercel origin into `CORS_ORIGIN`. If Vercel is not deployed yet, deploy Vercel first or use its preview URL, then rerun the Render deploy after updating the variable.
7. Keep the generated `JWT_SECRET`; do not replace it with a value from chat.
8. Deploy. The build installs dependencies, generates the Prisma client and compiles the server.
9. The start command runs `prisma migrate deploy` before starting the API. No reset command is used.
10. Verify `GET /api/health` returns `{"status":"ok"}`.

### Manual Render web service settings

If you create a normal **Web Service** instead of a Blueprint, use these exact fields:

| Field | Value |
| --- | --- |
| Branch | `main` |
| Root Directory | leave blank |
| Build Command | `npm ci --include=dev && npm run prisma:generate --workspace server && npm run build --workspace server` |
| Start Command | `npm run prisma:migrate:deploy --workspace server && npm run start --workspace server` |
| Health Check Path | `/api/health` |

The build must include dev dependencies explicitly because `NODE_ENV=production` makes `npm ci` omit pure dev dependencies such as `@types/node`. Do not use **Add from .env** in the Render dashboard; local `.env` files point to the local Podman database.

Production seeding is intentionally not automatic. The seed script is idempotent but creates demo users and permits. If demo accounts are required, use Render Shell and run:

```bash
npm run db:seed --workspace server
```

Run this only after confirming that demo data is appropriate for the production database.

## Vercel frontend setup

1. In Vercel, choose **Add New** then **Project**.
2. Import `Harishgbs/permit-to-work` from GitHub.
3. Keep the repository root as the root directory; `vercel.json` supplies the build command and `client/dist` output directory.
4. Add `VITE_API_BASE_URL` with the deployed Render URL including `/api`.
5. Deploy. Changing this variable requires a redeploy because Vite embeds it at build time.
6. `vercel.json` rewrites unmatched routes to `index.html`, so React Router paths work on refresh and direct navigation.

## Post-deployment verification

- `curl https://<render-service>.onrender.com/api/health`
- Open the Vercel URL and confirm the login page loads.
- Sign in with a seeded demo account if seeding was approved.
- Open browser developer tools and confirm no CORS errors.
- Confirm a protected API request succeeds from the deployed frontend.
- Create one disposable HOT_WORK permit and run a basic workflow without touching existing data.
- Confirm direct navigation to a permit detail URL loads after refresh.
