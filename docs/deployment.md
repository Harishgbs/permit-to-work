# Deployment guide

Architecture:

- Frontend: Vercel, built from `vercel.json` in the repository root.
- API: Render Node web service, defined by `render.yaml`.
- Database: Neon PostgreSQL, configured manually in the Neon and Render dashboards.

Deployed application:

- Frontend: https://permit-to-work-kappa.vercel.app
- Backend API: https://permit-to-work.onrender.com/api
- API health: https://permit-to-work.onrender.com/api/health

Never commit `.env` files or paste secrets into chat. The Blueprint generates `JWT_SECRET` in Render and leaves `DATABASE_URL` and `CORS_ORIGIN` for secure dashboard entry.

## Required environment variables

| Platform | Variable | Purpose |
| --- | --- | --- |
| Neon | none in repository | Create the PostgreSQL database and copy both its pooled and direct connection strings securely. |
| Render | `DATABASE_URL` | Pooled Neon connection string used by Prisma Client. Enter only in the Render dashboard. |
| Render | `DIRECT_URL` | Direct non-pooled Neon connection string used by Prisma CLI migrations. Enter only in the Render dashboard. |
| Render | `JWT_SECRET` | Generated by the Blueprint in Render; keep it private. |
| Render | `CORS_ORIGIN` | Deployed frontend origin: `https://permit-to-work-kappa.vercel.app`, without a trailing slash. |
| Render | `NODE_ENV` | Set to `production` by the Blueprint. |
| Render | `NODE_VERSION` | Set to `22` by the Blueprint. |
| Render | `PORT` | Provided automatically by Render. |
| Render | `JWT_EXPIRES_IN` | Optional; defaults to `1h`. |
| Render | `EXPIRY_SCAN_INTERVAL_MS` | Optional; defaults to `60000`. |
| Vercel | `VITE_API_BASE_URL` | Deployed API base URL: `https://permit-to-work.onrender.com/api`. |

## Neon setup

1. Sign in to Neon and create a new project for this assignment.
2. Create a separate production database; do not use the local Podman database.
3. Copy both the pooled and direct (non-pooled) PostgreSQL connection strings from the Neon dashboard. The pooled hostname contains `-pooler`; the direct hostname does not.
4. Keep both values private and enter them only into Render when prompted.

## Render API setup

1. In Render, choose **New +** then **Blueprint**.
2. Connect the GitHub repository `Harishgbs/permit-to-work`.
3. Select the `main` branch and continue.
4. Render reads `render.yaml` and prompts for `DATABASE_URL`, `DIRECT_URL` and `CORS_ORIGIN`.
5. Paste the pooled Neon connection string into `DATABASE_URL`.
6. Paste the direct Neon connection string into `DIRECT_URL`. Prisma Migrate uses this value because advisory locks are session-scoped and do not work reliably through a transaction pooler.
7. Enter the final Vercel origin into `CORS_ORIGIN`. If Vercel is not deployed yet, deploy Vercel first or use its preview URL, then rerun the Render deploy after updating the variable.
8. Keep the generated `JWT_SECRET`; do not replace it with a value from chat.
9. Deploy. The build installs dependencies, generates the Prisma client and compiles the server.
10. From a trusted local checkout with `DIRECT_URL` set in `server/.env`, run `npm run prisma:migrate:deploy -w server` once. The script skips automatically when `RENDER=true`, so an older Render start command that still calls it will not run migrations. Repeat this command only when new Prisma migrations are added.
11. Verify `GET /api/health` returns `{"status":"ok"}`.

### Manual Render web service settings

If you create a normal **Web Service** instead of a Blueprint, use these exact fields:

| Field | Value |
| --- | --- |
| Branch | `main` |
| Root Directory | leave blank |
| Build Command | `npm ci --include=dev && npm run prisma:generate --workspace server && npm run build --workspace server` |
| Start Command | `npm run start --workspace server` |
| Health Check Path | `/api/health` |

The build must include dev dependencies explicitly because `NODE_ENV=production` makes `npm ci` omit pure dev dependencies such as `@types/node`. Do not use **Add from .env** in the Render dashboard; enter production values directly there. Set `DATABASE_URL` to the pooled Neon URL and `DIRECT_URL` to the direct Neon URL in the service environment, and keep any separate local `.env` used for migrations out of version control.

## Production migrations

Migrations are intentionally not part of the API start command. After the first deploy and whenever a new Prisma migration is added, run this once from the repository root in a trusted local checkout with `DIRECT_URL` configured in `server/.env`:

```bash
npm run prisma:migrate:deploy -w server
```

Only one migration command should run at a time. No reset command is used. `scripts/migrate-deploy.mjs` exits immediately when `RENDER=true` unless `RUN_MIGRATIONS=1` is explicitly set, so normal Render restarts cannot take the advisory lock.

Production seeding is intentionally not automatic. The seed script is idempotent but creates demo users and permits. If demo accounts are required, run this from the same local checkout:

```bash
npm run db:seed -w server
```

Run this only after confirming that demo data is appropriate for the production database.

## Migration lock timeouts

If a manual migration fails with Prisma `P1002` while acquiring advisory lock `72707369`, do not retry repeatedly. Confirm that `DIRECT_URL` is set to the direct Neon connection string, ensure no second migration command is running, identify any stale advisory-lock holder, and then run `npm run prisma:migrate:deploy --workspace server` once. The direct connection is required because Prisma Migrate uses a PostgreSQL session-level advisory lock; transaction-mode poolers do not preserve that session state.

## Vercel frontend setup

1. In Vercel, choose **Add New** then **Project**.
2. Import `Harishgbs/permit-to-work` from GitHub.
3. Keep the repository root as the root directory; `vercel.json` supplies the build command and `client/dist` output directory.
4. Add `VITE_API_BASE_URL` with the deployed Render URL including `/api`.
5. Deploy. Changing this variable requires a redeploy because Vite embeds it at build time.
6. `vercel.json` rewrites unmatched routes to `index.html`, so React Router paths work on refresh and direct navigation.

## Post-deployment verification

- `curl https://permit-to-work.onrender.com/api/health`
- Open the Vercel URL and confirm the login page loads.
- Sign in with a seeded demo account if seeding was approved.
- Open browser developer tools and confirm no CORS errors.
- Confirm a protected API request succeeds from the deployed frontend.
- Create one disposable HOT_WORK permit and run a basic workflow without touching existing data.
- Confirm direct navigation to a permit detail URL loads after refresh.
